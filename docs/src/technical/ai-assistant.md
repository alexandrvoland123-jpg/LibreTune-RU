# Архитектура ИИ-ассистента

В этом документе описана техническая архитектура ИИ-ассистента LibreTune, работающего с языковой моделью, которую предоставляет сам пользователь. Документ предназначен для разработчиков, участвующих в развитии этой функции или расширяющих её возможности.

## Принципы проектирования

1. **Использование собственной модели** — LibreTune не размещает языковые модели. Пользователь самостоятельно указывает провайдера, ключ и модель. Благодаря этому функция не зависит от конкретного поставщика и сохраняет приватность.
2. **Только предложения, без самостоятельного применения** — ассистент формирует только проверенное и ограниченное допустимыми пределами *предложение*. Применение изменений и запись в ЭБУ всегда являются отдельными действиями, запускаемыми пользователем.
3. **Повторное использование существующих механизмов** — ассистент представляет собой тонкий слой над существующим перечислением `Action`, функцией `validate_action_set`, механизмами AutoTune и метаданными INI. Логика безопасности не дублируется.
4. **Независимость от провайдера** — единый trait `Provider` абстрагирует все backend языковых моделей. Оркестратор не работает с JSON конкретных провайдеров.

## Структура модулей

```
crates/libretune-core/src/
├── agent/
│   ├── mod.rs           # module root + re-exports
│   ├── orchestrator.rs  # multi-turn agent loop + ReadToolExecutor/TurnObserver traits
│   ├── tools.rs         # tool catalogue, CapabilityTier, catalogue_for_tier()
│   ├── context.rs       # context-gathering helpers (constants, tables)
│   ├── summarize.rs     # summarize_tune_context() aggregation
│   ├── safety.rs        # authority-limit clamping
│   ├── tiers.rs         # constant safety tiering (Safe/Caution/Dangerous)
│   └── apply.rs         # pure grid application of approved table actions
└── llm/
    ├── mod.rs           # module root
    ├── types.rs         # ChatRequest/ChatResponse/Message/ToolCall/LlmError
    ├── provider.rs      # Provider trait + factory
    ├── client.rs        # LlmClient (top-level entry point)
    └── providers/
        ├── openai.rs    # OpenAI Chat Completions (native protocol)
        ├── anthropic.rs # Anthropic Messages API (native protocol)
        └── google.rs    # Google Gemini generateContent (native protocol)
```

Уровень Tauri оборачивает эти модули в `crates/libretune-app/src-tauri/src/commands/agent.rs` (команды `agent_status`, `agent_send_message`, `agent_apply_proposals`), а также использует `commands/ai_keychain.rs` для хранения API-ключа в системном хранилище ключей ОС.

## Цикл работы агента

Один ход пользователя запускает **многошаговый цикл** внутри `orchestrator::run_turn` (с передачей управления `run_turn_observed`):

```
user message
     │
     ▼
┌─────────────────────────────────────────────┐
│  build ChatRequest (system + history + msg) │
│  + catalogue_for_tier(capability_tier)       │
└──────────────────────┬──────────────────────┘
                       ▼
              call Provider::chat
                       │
        ┌──────────────┴───────────────┐
        ▼                              ▼
  read tool calls?              propose tool calls?
        │                              │
        ▼                              ▼
  execute via                 tier gate → map → Action[]
  ReadToolExecutor            validate_action_set
  (TurnObserver emits          clamp to authority
   agent:progress)            accumulate into Proposal
        │                              │
        ▼                              ▼
  append tool-result                   │
  messages to history                  │
        │                              │
        ▼                              ▼
  loop back ─────────────►  (no reads left? → done)
                                   │
                                   ▼
                            return Proposal
```

Количество итераций ограничено `MAX_READ_ROUNDS` (6), чтобы контролировать стоимость запросов и не допускать бесконечных диалогов. Результаты чтения возвращаются модели в виде сообщений с результатами инструментов, чтобы перед окончательным ответом она могла анализировать реальные данные таблиц и констант.

Необязательный `TurnObserver` (`on_model_call` / `on_read_tool` / `on_complete`) позволяет уровню команд показывать ход выполнения, не связывая ядро с Tauri. `agent_send_message` реализует этот механизм через события `agent:progress`, которые панель чата отображает как текущую активность, например «чтение veTable1…».

## Trait Provider

```rust
#[async_trait]
pub trait Provider: Send + Sync {
    fn name(&self) -> &str;
    async fn chat(&self, req: &ChatRequest) -> Result<ChatResponse, LlmError>;
}
```

Каждый конкретный провайдер преобразует универсальный `ChatRequest` в собственный формат передачи (OpenAI `tools[]`, блоки Anthropic `tool_use`, Gemini `functionDeclarations`), обращается к своей конечной точке через общий клиент `reqwest` и преобразует ответ обратно в универсальный `ChatResponse`. Для добавления нового провайдера достаточно реализовать этот trait — менять оркестратор не требуется.

## Trait ReadToolExecutor

```rust
#[async_trait]
pub trait ReadToolExecutor: Send + Sync {
    fn handles(&self, tool_name: &str) -> bool;
    async fn execute(&self, tool_name: &str, arguments: &str) -> String;
}
```

Основная библиотека определяет этот контракт. Уровень Tauri реализует его в `LiveReadExecutor`, который получает доступ к `AppState` через `tauri::Manager::state()` и читает таблицы/константы на основе загруженного описания ЭБУ и калибровки. Такое разделение позволяет тестировать цикл отдельно, без реального провайдера или ЭБУ.

## Каталог инструментов

Определён в `agent/tools.rs`. Модель может вызывать следующие инструменты:

| Инструмент | Тип | Назначение |
|------|------|---------|
| `list_tables` | read | Получение имён, назначений и размеров таблиц |
| `read_table` | read | Получение значений таблицы, узлов осей и единиц измерения |
| `read_constant` | read | Получение значения константы, min/max и вариантов |
| `list_features` | read | Список констант-переключателей функций (bits) |
| `summarize_tune_context` | read | Сводные данные об охвате, ошибке AFR и аномалиях |
| `tune_health_check` | read | Оценки состояния отдельных областей |
| `get_realtime_snapshot` | read | Текущие значения датчиков (один опрос ЭБУ, отобранные каналы) |
| `query_datalog` | read | Сводная статистика или последние строки текущего сеанса/сохранённого журнала |
| `propose_table_edit` | propose | Подготовка изменения одной ячейки (с проверкой и ограничением) |
| `propose_bulk_operation` | propose | Подготовка масштабирования/сглаживания/интерполяции (с проверкой) |
| `propose_constant_change` | propose | Подготовка изменения константы (с учётом уровня доступа) |

### Уровни возможностей

`tools::CapabilityTier` (`Read` ⊂ `Tune` ⊂ `Config`), считываемый из настройки `ai_capability_tier` (неизвестные значения преобразуются в `Read`), определяет, какие инструменты может вызывать модель:

- **Read** — только инструменты чтения.
- **Tune** — чтение и `propose_table_edit` / `propose_bulk_operation`.
- **Config** — возможности Tune плюс `propose_constant_change`.

Проверка выполняется на двух уровнях: `catalogue_for_tier()` фильтрует список инструментов для каждого запроса, поэтому модель не получает инструменты выше своего уровня; `map_tool_call` безусловно отклоняет любые предложения, не соответствующие уровню доступа. Это дополнительная защита от вымышленных вызовов инструментов.

### Процесс применения

`agent_apply_proposals` проверяет и затем **применяет** одобренные действия (сам оркестратор и модель этого делать не могут):

1. Каждое действие повторно проверяется по загруженному описанию ЭБУ (отдельный `ActionSet` для каждого действия); действия с ошибками пропускаются с сообщением об ошибке.
2. Перед любой записью создаётся **точка восстановления** (`create_restore_point_internal`).
3. Действия с таблицами группируются по таблицам: одно чтение (`get_table_data_internal`) → применение изменений средствами ядра через `agent::apply::apply_table_actions_to_grid` (преобразование `(x, y)` в `(row, col)`, передача пакетных операций в `table_ops`) → одна запись (`update_table_z_values_internal`, тот же путь, который используют редакторы таблиц: кэш + копия калибровки + необязательная запись в RAM ЭБУ). Если группа завершается ошибкой, отклоняется вся группа.
4. Константы обрабатываются через `update_constant_internal`; для констант типа bits также выполняется проверка конфликтов контактов.
5. Для каждой таблицы выводится **предупреждение о смещении**, если принятые изменения сдвигают среднее значение изменённых ячеек более чем на 10%.
6. В соответствии с `auto_commit_on_save`: режим *always* сохраняет калибровку и создаёт коммит (репозиторий автоматически не инициализируется); режим *ask* возвращает подготовленное сообщение коммита.

**Запись (Burn) никогда не выполняется автоматически.** Подготовленные изменения попадают в RAM ЭБУ так же, как при ручном редактировании таблицы; команда Burn остаётся отдельным действием пользователя.

## Определение TableRole

`EcuDefinition::infer_table_roles()` присваивает каждому `TableDefinition` машинно-читаемое значение перечисления `TableRole` (`Ve`, `Ignition`, `AfrTarget`, `WarmupEnrichment`, `Other`) на основе разделов `[VeAnalyze]` и `[WueAnalyze]` файла INI. Благодаря этому ассистент определяет назначение таблицы, не пытаясь угадать его по имени.

## Дополнения к проверке корректности

Для ассистента потребовалось расширить `ActionPlayer::validate_action_set`: теперь функция проверяет не только существование объектов, но и:

- **`min`/`max` константы** (границы в единицах отображения);
- **диапазон хранения исходного значения `DataType`** (до масштабирования);
- **границы индексов ячеек таблицы** (`x_index`/`y_index` относительно `x_size`/`y_size`);
- **перечисление для типа bits** (значение должно быть допустимым индексом варианта).

## Интерфейс Frontend

- `components/agent/AgentSidePanel.tsx` — закреплённая правая панель (заголовок, маркер изменения размера, кнопки отдельного окна/сворачивания, сворачиваемая очередь проверки, переключатель чатов, счётчик токенов для каждого чата).
- `components/agent/ChatPanel.tsx` — история диалога и поле ввода; отслеживает `agent:progress` (текущую активность), передаёт `unit_prefs` для каждого хода и принимает `extraContext` / `prefill` для сценария Ask AI.
- `components/agent/ProposalQueue.tsx` — интерфейс проверки отдельных предложений; отображает предупреждения о конфликтах контактов и пакетных изменениях, а также итог применения.
- `components/tables/TableToolbar.tsx` — кнопка **Ask AI**; отправляет событие `agent:ask` с таблицей, заголовком, осями и выделением. `App.tsx` открывает панель по этому событию; `AgentSidePanel` добавляет контекст в системный запрос следующего хода и предварительно заполняет поле ввода.
- `components/common/RiskAcknowledgement.tsx` — повторно используемый компонент подтверждения риска.
- Панель можно вынести в отдельное окно с помощью существующей системы `WebviewWindow` и маршрутизации по hash (см. `PopOutWindow.tsx`, тип `agent`).

## Хранение API-ключа

`commands/ai_keychain.rs` хранит API-ключ в системном хранилище ключей ОС (библиотека `keyring`: Windows Credential Manager, macOS Keychain, Linux Secret Service). Ключи в открытом виде, обнаруженные в файле настроек, при первой загрузке переносятся в системное хранилище; при сохранении копия в файле очищается, если ключ уже находится в системном хранилище. Все операции предусматривают безопасный резервный режим: если хранилище ключей недоступно (например, Linux без графической среды или заблокированный сеанс), сохраняется прежнее поведение с хранением ключа в файле, чтобы работа ассистента не нарушалась.

## Обработка ошибок

- Уровень ядра использует типизированное перечисление `LlmError` (`Network`, `Auth`, `RateLimit`, `Parse`, `ApiError`, `Config`).
- На границе команд Tauri ошибки преобразуются в `Result<T, String>`.
- Настройки сохраняются независимо друг от друга: ошибка при сохранении одного параметра не отменяет сохранение остальных.
- Ошибки инструментов чтения возвращаются *модели* в виде JSON `{"error": …}`, чтобы она могла продолжить рассуждение другим способом. Если указано неверное имя журнала данных, в ответ дополнительно включается список доступных журналов, чтобы модель могла повторить запрос.
